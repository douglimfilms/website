# Doug Lim Films — Wedding Documentation Site

Static one-page site for a documentary-style, multi-camera wedding videography side business (LA-based), run under the videographer's own name. Positioning: real audio + multi-angle coverage, explicitly NOT cinematic/staged wedding videography.

**Business renamed from "Field Coverage" to "Doug Lim Docs," then to "Doug Lim Films."** Reasoning for dropping "Field Coverage": personal-name branding builds more trust for a solo wedding videographer than an abstract company name (couples want to know *who* is shooting their day) — "Field Coverage" read more like a journalism/broadcast outfit and never actually evoked weddings. "Doug Lim Media" was considered and rejected at that point: the domain (`douglimmedia.com`) has an awkward double-M letter collision where "Lim" meets "Media." "Docs" was chosen next — collision-free as a domain (`douglimdocs.com`, confirmed available), and it reinforced "documentary-style," the differentiator. **"Docs" was then dropped after real-world feedback: people didn't like it** (read as paperwork/"docks," not evocative of video) — renamed again to "Doug Lim Films," a plain, unambiguous genre term with no collision risk and no confusing double meaning. Renamed in `index.html`: `<title>`, `.brand` nav text, and the footer copyright line — check all three if renaming again.

## Known decisions / history worth knowing before changing things
- **Fonts are system fonts on purpose.** An earlier version used Google Fonts and rendered completely blank in some preview contexts. Don't reintroduce external font requests without testing carefully.
- **Hero video:** muted, autoplay, loop, `playsinline`, `preload="auto"`. Must be faststart-encoded (`ffmpeg -c copy -movflags +faststart`) or it loads very slowly — moov atom needs to be at the front of the file. Re-run this any time the video is re-exported.
- **Two hero video formats, WebM listed first:** `ceremony-loop.webm` (VP9) is served before `ceremony-loop.mp4` (H.264) in the `<source>` list — most modern browsers pick the WebM (currently ~1.5MB vs ~5.1MB for the same visual quality), older/Safari-without-VP9-support falls back to the MP4. Re-encode commands used (18.4s, 1920x1080 source):
  - MP4 fallback: `ffmpeg -i src.mov -c:v libx264 -preset slow -crf 21 -profile:v high -level 4.1 -pix_fmt yuv420p -an -movflags +faststart ceremony-loop.mp4`
  - WebM primary: `ffmpeg -i src.mov -c:v libvpx-vp9 -b:v 0 -crf 32 -row-mt 1 -pix_fmt yuv420p -an -deadline good -cpu-used 2 ceremony-loop.webm`
  - Both files must be re-generated together any time the source footage changes — keep CRF values as-is unless quality/size checks say otherwise.
- **Always re-encode from the original camera export, never from a HandBrake (or other lossy) intermediate.** Re-encoding an already-compressed file bakes in and can amplify its compression artifacts (generation loss) instead of starting from clean detail — this cost real quality once already. Keep the original raw/high-bitrate export around specifically for re-encoding the hero loop.
- **Monitor wall tiles are all equal size on purpose** — an earlier version had CAM A spanning 2×2 as a "big tile" with the others small, which left uneven boxes and an awkward empty grid cell. Now `.wall` is a plain `repeat(4, 1fr)` grid (all four tiles same size: CAM A, CAM B, CAM C, AUD). On the ≤760px breakpoint it drops to `repeat(2, 1fr)` for a clean 2×2, no extra CSS needed. (A 5th "PGM" tile — the full edited multi-cam cut, same source as the hero — was tried and removed once the hero itself looked good enough on its own; if re-adding a 5th tile, re-solve the empty-cell problem, e.g. with a `repeat(5, 1fr)` grid and a spanning rule for the trailing tile on mobile.)
- **Monitor wall tiles (CAM A/B/C) play real synced footage, encoded small on purpose.** The trick is encoding at the tile's actual rendered size instead of shrinking a 1080p file with CSS — bitrate scales with resolution, so this is what keeps 3 extra autoplaying videos from meaningfully slowing the page down (all three together are under 800KB in WebM). Encode command (source cropped from 16:9 to a centered 4:3 region first to match the tile aspect ratio, `crop=1440:1080:240:0`, then `scale=480:360`): same `libx264 -preset slow -crf 23` / `libvpx-vp9 -crf 34 -b:v 0` settings as the hero video otherwise. If the grid layout changes tile proportions again, re-crop/re-scale to match (tile size = `(1024 - gaps) / column count`, retina 2x, rounded to a clean 4:3 pair).
- **Hero video is the master clock for the whole monitor wall.** All wall-tile `<video>` elements (`class="wall-cam-video"`) and the hero (`id="hero-video"`) have no `loop` attribute — looping is handled manually in JS so every tile restarts at frame 0 together instead of drifting apart on independent native loops. A periodic drift check re-syncs any tile that's off by >0.12s. This only works because all source clips are cut from the same synced 18.42s take — if new footage is added with a different length/sync point, this logic needs revisiting.
- **Monitor wall timecodes are driven by real video `currentTime`**, not a fake incrementing counter — they loop with the ~18.4s clips instead of counting up forever. AUD has no video of its own so its timecode mirrors CAM A's, since all tiles are the same synced moment (and now that everything follows the hero's master clock, all timecodes on the page match).
- **On mobile (≤480px), `header.hero` gets a shorter `min-height` (480px vs. 620px) and less padding.** The hero video is 16:9 footage in a much taller/narrower container on phones, so `object-fit: cover` has to crop a lot of the frame's width to fill it — subjects can end up pushed toward the edges. Shortening the container brings its aspect ratio closer to the video's native 16:9, which needs less horizontal cropping, so more of each frame stays visible. This is a general fix (helps across the whole loop, since the hero cuts between several camera angles over its ~18s, not one continuous shot) rather than an `object-position` tweak for one specific moment, which would only fix the instant it was tuned for and could make other cuts worse. If mobile framing issues persist, check other cuts in the loop before adjusting further — don't fix one frame at the expense of others.
- **Hero is boxed (max-width: 1080px, bordered), not full-bleed edge-to-edge** — changed from an earlier full-viewport-width treatment. Two reasons: (1) full-bleed meant the 1920px source could get upscaled beyond native resolution on wide monitors, and even at normal desktop widths the video was closer to its native size, so compression softness was more visible than on the smaller A/B comparison video; boxing it to ~1024px display width means the browser is always downscaling the source, which looks sharper. (2) It also now matches the page's content width instead of being the one full-bleed element. On the ≤1080px breakpoint the left/right border and top margin drop out so it reads as full-bleed again on tablet/mobile, matching the original behavior there. If the hero ever needs to go back to full-bleed, expect the quality gap vs. the A/B video to reappear — the fix would then be re-encoding at a higher bitrate instead.
- **Hero has no CTA buttons anymore** ("Check a date" / "See what's different" removed, along with the now-unused `.cta-row` CSS). The hero is `align-items:flex-end`, so removing the bottom-most element in `.hero-card` shifted the headline/subtext down toward the bottom of the frame — that's a natural consequence of the existing flex layout, not a separate positioning change. If CTAs are ever added back here, expect the text to shift back up accordingly.
- **Hero subtext is now one line: "High-fidelity audio/video coverage of your day."** — replaced the longer three-sentence paragraph ("Multi-camera wedding documentation — vows, toasts... Not a highlight reel built around a shot list."). Came out of a conversation about what the hero subtext section is actually *for* — worth noting for next time: the company name lives in the nav brand (`.brand`, top-left), not the hero subtext; the hero subtext is just descriptive copy under the H1 headline. Company naming itself ("Field Coverage" vs. alternatives) was still an open, unresolved conversation as of this change — don't assume it's settled just because this copy landed.
- **Hero headline's emphasized phrase changed from "no staging." to "authentically you."**, and its color from the tally-red family (`#FF8A75`) to a warm gold (`#D4A94E`) — set in `header.hero h1 em.hl` / `header.hero h1 .hl em` (this overrides the plain `.hero h1 em{color:var(--tally)}` fallback, which is why changing `--tally` alone wouldn't have touched this). Gold was chosen live, compared directly against a dusty-rose alternative (`#E0A9A0`) via screenshot — rose read too close to the original red/coral to feel like a real departure, gold felt more distinct and more "wedding-elevated" (rings, champagne) rather than romantic-soft. If revisiting this color, that's the comparison basis — don't re-litigate red-family options without a genuinely different hue.
- **Hero H1 has a mobile-only font-size override, `@media (max-width:480px){ .hero h1{ font-size:16px; } }`, added after the base `clamp(24px, 3vw, 34px)` still wrapped "No performance, authentically you." onto 3 lines at narrow widths.** The clamp's own 24px floor wasn't small enough — even 18px and 20px still wrapped "you." onto its own line at 320px specifically (375px was fine earlier, but 320px is the width that actually forced this down to 16px). If the headline copy changes again and gets shorter, this override may no longer be needed — re-check at both 320px and 375px before removing or loosening it, not just 375px alone.
- **Hero text legibility over video** went through several iterations: solid card (too heavy/covered subjects) → per-line highlight boxes (still felt block-y) → transparent text with heavy layered text-shadow, no background → an earlier full-video `.hero-veil` (light paper-tint wash + `backdrop-filter: blur(1.5px)`) was removed because it hazed the whole video without actually helping contrast (a *light* tint doesn't help *light* text against bright content) → tried a soft dark radial scrim behind just the text block (`.hero-card::before`), which did verifiably fix the legibility risk, but was removed again on sight — didn't like the look. **Current state: transparent text + heavy text-shadow only, no scrim, no veil.** The underlying risk is still real and unaddressed: a bright frame (white dress, window) passing behind the text — especially the smaller subtext/button — can be hard to read, verified worst-case around `hero-video.currentTime = 13s`. If this becomes a real problem, next things to try: trim/re-time the loop to avoid the worst frames behind the text position, or a different legibility approach than a scrim (e.g. moving the text to a less busy region of frame, matching how the location label was already moved to the nav for this exact reason below).
- **Location label** ("Los Angeles, CA") was moved out of the hero and into the top nav bar for exactly this reason — anything sitting on the plain paper nav background doesn't have the video-legibility problem at all. Consider doing the same for other hero elements if legibility issues persist.
- **Mobile nav (≤640px) shows all links directly, wrapped across lines — not a hamburger menu.** An earlier version just hid `.navlinks` entirely below 640px with no replacement, which meant phone visitors had no way to reach any section at all (a real bug, not a style choice — caught and fixed). A hamburger/accordion version was built next (button toggles `#mobile-nav` open, pushing page content down rather than a full-screen overlay), but the user didn't want a hidden-menu pattern at all, even a non-blocking one — preferred every link always visible with zero taps. Fix: `"The Difference"` shortened to `"Difference"` (only genuinely long label), font-size/gap reduced on mobile, and `.navlinks` allowed to `flex-wrap` across 1–2 lines instead of forcing a single row or hiding.
  - Nav is now 5 links (`Difference`, `Services`, `Sample`, `Rates`, `Contact`) — `Process` was removed from the nav as "not really important" (the `#process` / "HOW IT WORKS" section itself is untouched, still on the page, just not linked from nav). At 5 links: fits on one line at 375px+ (most modern phones); at 320px (iPhone SE-class), `Contact` still wraps to its own second line — same pattern as before, fewer items. No overflow at either width. If more nav items are ever added or removed, re-check wrapping at 320px before assuming it still fits — don't reach for a hamburger as the default fix here, that was explicitly rejected once already.
- **Services/rates are wedding-only** — an earlier version of this site also covered recitals and little league; that content was deliberately stripped when the business focus narrowed to weddings only.
- **Callsheet ("WHAT YOU GET" / "WHAT YOU DON'T GET") items are short phrases, not full sentences — trimmed twice.** Originally 6 items per column, each a full explanatory sentence with a sub-clause (e.g. "Multiple synced camera angles, cut together — not just one static wide"). First pass: cut to 5 items per column, core phrase only. Second pass: merged "Multiple synced camera angles" + "Clean lav mic audio" into one line ("Multiple synced camera angles with clean lav mic audio") and dropped "A story reordered for pacing" entirely — now 4 items per column, evenly balanced. Third pass: swapped "Drone flyovers or a trailer cut" for "Viral TikTok transitions that age fast" — brings back the "trend-chasing edits that feel dated within a year" idea from the original 6-item version (cut in the first pass), now as a short phrase naming the platform directly for relatability. Fourth pass: reworded "Footage that holds up for decades" to "Footage that's elegant and timeless" and moved it from last to 2nd in the GET list (right after "every vow, toast, and reading"). Fifth pass: the two lists are now deliberately paired line-by-line as opposites, not just independently curated — swapped "Posed 'candid' shots" for "Shaky cell phone video with muffled audio" (reworded once more from an interim "One static angle with muffled camera audio") specifically to oppose GET's line 3 ("Multiple synced camera angles with clean lav mic audio"). **If either list is edited again, keep the pairing intact** — GET line N and DON'T-GET line N should read as opposites (1: real full record vs. staged re-shoots; 2: elegant/timeless vs. trendy/dated; 3: multi-cam+clean audio vs. single-cam+muffled audio; 4: fast turnaround vs. six-month wait). Reordering or replacing one side without the matching change on the other breaks this.
- **On-board vs. lav mic comparison lives inside the `#difference` section**, labeled "ON-BOARD MIC VS LAV MIC" — not in its own standalone section. It was originally two separate sections (`#audio-compare`, `#audio-compare-toggle`); both ids were removed when merged in, so if anything still references them (nav links, anchors), update to `#difference`.
  - **It comes *before* the "WHAT YOU GET"/"WHAT YOU DON'T GET" callsheet, not after** — originally placed below the callsheet, but moved above it because the callsheet is a dense two-column bullet list ("a wall of text") and the concern was visitors would disengage before scrolling far enough to reach the interactive audio toggle. Leading with something to click/listen to first, then following with the reasoning/detail in list form, was judged better for engagement than reading-then-interacting. If reordering this section again, keep the interactive element first.
  - **Current version: two independent boxes** (`.wa-box[data-source="onboard"]`/`"lav"`), each a single `<video>` with its own real embedded audio (muxed video+audio file, not a muted video paired with a separate `<audio>` element). Pressing one pauses the other and carries over its exact `currentTime` before playing, so switching mid-comparison still lands on the same moment — but only one video is ever actually playing at a time. This sidesteps the entire class of dual-simultaneous-playback sync bugs documented below, at the cost of switching being a position-jump instead of an instant simultaneous toggle. Plays once per box, then stops (`ended` resets that box's `currentTime` to 0 while paused, ready for a fresh replay). A `.playing` class on `.wa-box` drives a highlighted border so it's visually clear which one is active. `.wa-box-label` (the "ON-BOARD MIC"/"LAV MIC" caption under each box) was bumped from small/soft/regular-weight to bold, full-ink, 13px — the initial styling was too subtle to read as a real label rather than incidental fine print. It also turns tally-red while that box is playing, matching the border highlight.
  - **Boxes are deliberately small and stay side-by-side even on mobile** — `.wa-boxes` is a 2-column grid capped at `max-width:500px` (roughly matching the monitor wall's tile scale) with `width:100%`, so it shrinks proportionally on narrow viewports rather than stacking to one column. The underlying video files are encoded at their actual small display size (480×270) rather than a larger file shrunk via CSS, same principle as the monitor wall tiles — see the encode command in the Files section above.
  - **Earlier architectures, all replaced — read "Hard-won lessons" below before rebuilding any of these again:** (1) an original side-by-side two-clips version ("Option A", deleted files); (2) a single-video toggle built on the Web Audio API (decode once, switch `AudioBufferSourceNode`s from a shared clock) — abandoned after real-device debugging found Web Audio API output can be silently gated on iOS; (3) a single-video toggle built on two real `<audio>` elements playing continuously in the background, switching by mute — this one actually worked for audio, but kept needing new fixes for the muted video's sync to whichever track was active (drift correction, cold-start lag between video and audio starting, native-loop phase drift), each fix surfacing a new real-device problem. **A known-good snapshot of that `<audio>`-element toggle version (confirmed stutter-free on a real phone, before the two-box rebuild) is saved at `backups/index-ab-toggle-clean-fallback.html`** — if the two-box version doesn't hold up, this is the fallback to restore from (copy it back over `index.html`, re-sync to `deploy/`). Keep this backup current if a future rebuild of this feature holds up well.
  - **Hard-won lessons from the debugging process that led here — worth reading before changing this feature again:**
    - The Web Audio API can end up silently gated on iOS: its shared audio session category can respect the hardware silent switch unless a real HTMLMediaElement has already played on the page. This is a platform limitation, not a code bug — nothing done purely inside the Web Audio API (resuming in a gesture, priming with a silent buffer) reliably fixed it. Real `<audio>`/`<video>` elements don't have this problem.
    - **Forcing a discrete seek (`currentTime = x`) on a video or audio element — even a small one — was consistently disruptive on real mobile devices, regardless of how far off it was correcting.** Every "keep it continuously in sync" strategy tried (periodic seeking at various thresholds/intervals, even a smooth `playbackRate` nudge) either caused visible stutter or, in one case, left an audio track silently stuck after being repeatedly re-seeked in the background. Only correct at deliberate, expected moments (a toggle click, a loop restart) — don't reintroduce continuous background correction.
    - A native `loop` attribute on the video seems like a good way to avoid a manual seek-to-0 every loop, but it lets the video wander onto its own independent loop schedule, decoupled from when the audio actually loops — the two can end up out of phase by up to a full loop length. Keep the video's reset explicitly tied to the same event that resets the audio.
    - Always regenerate a video's poster image (`ffmpeg -i file.mp4 -vframes 1 -q:v 2 poster.jpg`) any time the video file itself is re-encoded — a stale poster causes a visible flash/glitch the moment playback starts, since the browser swaps from the poster to the real first frame.
    - Guessing at mobile-only fixes without on-device evidence produced several regressions in a row. A temporary, visible on-page debug readout (writing to a DOM element, since a phone's console isn't reachable without plugging into a Mac) was what actually cracked each real bug in this saga. If mobile-only issues resurface, reach for that technique again early, not as a last resort.
  - **Testing note:** when checking play/pause/toggle behavior on this clip, use tight synchronous checks (or short `await`+`setTimeout`) rather than separate sequential tool calls with real delay between them — the clip is only ~17s long, and cumulative round-trip latency across multiple separate checks can exceed that, making a clip that finished playing naturally look like a bug.
  - **For real mobile testing, serve the folder locally instead of redeploying to Netlify on every change** (`python3 -m http.server 8000 --bind 0.0.0.0` from this folder, then visit `http://<mac-lan-ip>:8000/index.html` from a phone on the same Wi-Fi) — avoids burning Netlify's free-tier deploy credits, and is actually more accurate than opening `index.html` via `file://`, since `fetch()` doesn't behave reliably from `file://` on mobile Safari. Reload the page on the phone after each fix; no redeploy needed. Use a cache-busting query string (`?t=2`, `?t=3`, ...) each time, since Safari/Chrome on iOS each keep their own separate cache and can otherwise silently keep serving a stale version.
- **Back-to-top button** (`.back-to-top`, fixed bottom-right) fades in once scrolled past 0.75× viewport height and fades out near the top again — plain scroll-position toggle, no library. Click scrolls to `top:0`; uses `behavior:'smooth'` unless `prefers-reduced-motion` is set, in which case it jumps instantly, consistent with how motion is gated elsewhere on this page (rec-dot, waveform, spinner).
- **A/B toggle clip currently plays once and stops** (see the A/B toggle section above for the full history — it looped forever for a while after a Web-Audio-API-to-`<audio>`-element rebuild, then was changed to play-once-and-stop). An auto-stop-*after-2-loops* feature existed even earlier than that and was lost along the way — flag to the user if that specific behavior (2 loops, not just 1 play) is still wanted, since it was an explicit past request, not a deliberate removal.
- **"How It Works" (`#process`) is 4 steps now, not 3: Inquiry → Coordination → Day-of Coverage → Delivery.** Two changes: (1) dropped "site check" from step 1 — the videographer doesn't do in-person venue site visits, so the copy no longer implies one ("I confirm availability and flag anything the venue requires" → "I confirm availability and get the details I need to plan the day"). (2) Added a new "Coordination" step: he coordinates directly with the couple's planner/DJ/photographer ahead of time, framed as one less thing for the couple to manage — a real value-add that wasn't represented anywhere on the site before. `.steps` grid updated from `repeat(3, 1fr)` to `repeat(4, 1fr)` with a new `900px` breakpoint for a 2×2 tablet layout (previously jumped straight from 3-across to single-column at 760px); verified clean at desktop (4-across), ~800px (2×2), and mobile (stacked).

## Deployment
**Live at `www.douglimfilms.com` (custom domain) via GitHub Pages, DNS on Cloudflare.** Repo: `github.com/douglimfilms/website`, deployed from the `deploy/` folder's `main` branch, root — `field-coverage-site/` (this folder) is the working/source folder and was deliberately kept out of git (it also has ~400MB of raw source `.mov` footage, never deployed, plus a `backups/` folder). Established workflow: edit files in `field-coverage-site/`, copy the changed ones to `deploy/`, then from `deploy/` run `git add -A && git commit -m "..."` and `git push`. Auth for `push` is a GitHub **Personal Access Token** (Settings → Developer settings → Personal access tokens on github.com), not a password — the account signs into the GitHub *website* via Google OAuth, which is unrelated to git's own HTTPS auth; `git fetch`/`git pull` work anonymously without a token since the repo is public, only `push` needs one.

- **Custom domain DNS:** a `www` CNAME record pointing to `douglimfilms.github.io`, plus 4 apex `A` records (185.199.108.153, .109.153, .110.153, .111.153) so the bare `douglimfilms.com` also resolves and GitHub auto-redirects it to the `www` version. `CNAME` file in `deploy/` sets the custom domain on the GitHub Pages side. All DNS records are set to "DNS only" (Cloudflare proxy off) — proxying was left off deliberately so GitHub could directly verify domain ownership and issue its own SSL certificate; enabling Cloudflare's proxy later is possible but adds complexity (would need SSL/TLS mode set to Full) and isn't necessary for a small static site.
- Cloudflare was originally set up to deploy via Workers (`npx wrangler deploy`), but that path was abandoned before ever deploying — it targets Workers server-side projects and needs a `wrangler.toml` this repo doesn't have. GitHub Pages was simpler and more direct for a plain static site with zero build step.
- **A one-time gotcha worth remembering:** after setting the custom domain in GitHub's Pages UI, GitHub's website itself commits a `CNAME` file directly to the branch (a real commit, done through their web interface) — if a `CNAME` file was also just added locally (as happened here), the next `git push` gets rejected with diverging histories. Fix: `git fetch origin` then `git merge origin/main` (trivial since both sides typically add identical content), resolve the CNAME conflict by keeping the (identical) content, commit, then push again.
- **Contact form (`#contact`) is wired to Formspree**, not Netlify Forms (this site isn't on Netlify) and not a `mailto:` form (unreliable UX, depends on the visitor having a configured mail client).
